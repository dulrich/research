# Memory measurement calibration: what each memory source counts

A calibration of the memory numbers a container run can produce — the cgroup `memory.peak`, sampled cgroup `anon`/`file` high-water marks, the process's own `VmHWM`, and settled anon after a workload-complete boundary — against allocations of known size, against concurrent file I/O, against glibc allocator retention at several CPU counts and settle windows, and against the probe's own overhead. All numbers come from the in-container probe `scripts/memprobe.sh` driven by `scripts/measure.mjs`; the tables below quote the generated `results/<class>/report.md` files.

## Question

Memory claims need to say which source they read and what that source counts. Which of `memory.peak`, sampled `anon`/`file`, and `VmHWM` recovers an allocation of known size, how much does page cache contaminate each, what does glibc retain after multithreaded churn and does it settle with time or depend on the CPU count, and what does the probe itself cost?

Rigor: **standard** (`../methods/timing.md`: interleaved invocations, warm-up rounds, padded environment, A/A pair per class, hierarchical bootstrap), with one stated exception to R5: each variant is one build of one program, so the report's "builds" column is 1 and layout variation is limited to environment padding. Host labelling per `../methods/live-host.md`: pinned (`--cpuset-cpus` inside CCD1), user live. Pilots (R9) are under `results/pilot/` and are excluded from inference.

## Method

- **Probe** (`../scripts/memprobe.sh`, POSIX sh): runs the command in the background, samples `/sys/fs/cgroup/memory.stat` (`anon`, `file`) and the command's `/proc/<pid>/status` (`VmHWM`, `RssAnon`) every `--interval` seconds, reads `memory.peak` after the command exits, and prints `MEASURE` lines. `memprobe.sh --help` lists the metrics:
  - `cgroup_peak_mib`: `memory.peak` of the container's cgroup after the command exited (anon plus file, includes the probe and the container's start-up).
  - `cgroup_anon_hwm_mib`, `cgroup_file_hwm_mib`: highest sampled `anon` / `file` of `memory.stat`.
  - `vmhwm_mib`: the command's `VmHWM` at its last sample before exit.
  - `anon_settled_<S>s_mib` (cgroup `anon`) and `rssanon_settled_<S>s_mib` (command `RssAnon`) at the first sample at or after boundary+S.
- **Boundary rule:** settled values are read only after the workload signals completion (`--boundary-line STR` on stdout or `--boundary-file F`) while the command is still alive, as offsets from the boundary; several windows are sampled in one block. A window the command does not stay alive for, or any window without a boundary, is not emitted (stderr note). A time series from launch or after exit is never used.
- **Programs** (`src/`, built in `Dockerfile`): `alloc` mallocs N MiB and touches every page, optionally writes M MiB to a file on another thread (buffered, no fsync), prints `BOUNDARY`, holds 1 s, then self-reports its `VmHWM` and the cgroup peak (`self_*` metrics). `churn` runs 12 threads of mixed-size malloc/free for 5 s (after the K3s program of `../live-host-measurement-confounds/`), joins them, prints `BOUNDARY`, stays idle 126 s, then self-reports `RssAnon` and the malloc arena count.
- **Run wrapper** (`run.sh`): one throwaway `docker run --rm --cpuset-cpus …` per invocation; mounts the probe; for the churn class appends `bad_mode_<S>s` (1 when `anon_settled_<S>s_mib` exceeds the pilot-fixed threshold, else 0).
- **Configs** (`configs/*.json`, generated by `gen-configs.mjs --bad-mib 420`): every metric has a `metrics` entry (level, lower is better; bad-mode as `rate`). Pilot configs in `configs/pilot/`.

## Results

Host: the measurement host, a 12-core desktop (AMD Ryzen 9 7900X, SMT on), kernel 7.2.12+deb13-amd64, in use by its owner (live). Containers pinned to CCD1 CPUs 6-11,18-23 (or 6-11, or 6,7 where stated). CPU pressure (`/proc/pressure/cpu`, "some") sampled each minute during the batch (200 samples, `avg60` mean 2.98, maximum 39.5, above 10 in 7 samples); the batch ran a (about 5 min), b, d, then c (about 4 h). All medians are MiB with the report's 95% interval.

### Class a: known anonymous allocations (standard, 30 invocations + 3 warm-up per variant, A/A a64 vs a64-copy)

`results/a/report.md`. Known allocation 16 / 64 / 256 MiB, every page touched; `a0` is the same program allocating nothing.

| source | a0 | a16 | a64 | a256 | bias vs known (16 / 64 / 256) | A/A half-width (ratio) |
| --- | --- | --- | --- | --- | --- | --- |
| `rssanon_settled_0s_mib` (process anon) | 0.12 | 16.11 | 64.11 | 256.1 | +0.11 each; minus a0: -0.01 / -0.01 / -0.02 | 0 |
| `anon_settled_0s_mib` (cgroup anon) | 5.91 | 16.3 | 64.3 | 256.3 | +0.30 each; a256 - a16 = 240.0 | 0 |
| `cgroup_anon_hwm_mib` | 5.91 | 16.31 | 64.31 | 256.3 | +0.3 each | 0.0011 |
| `vmhwm_mib` | 1.42 | 17.42 | 65.43 | 257.4 | +1.4 each (a0: 1.42) | 0.00069 |
| `self_vmhwm_mib` (bare self-report) | 1.44 | 17.45 | 65.45 | 257.4 | +1.4 | 0.00069 |
| `cgroup_peak_mib` | 9.49 | 25.29 | 73.42 | 265.7 | +9.3 / +9.4 / +9.7 | 0.0056 |

Confidence intervals on the anon sources are about 0.01-0.1 MiB wide (for example a64 `anon_settled_0s_mib` [64.3, 64.3]), so none of the raw medians contains the known size: each source carries a constant offset that the 0 MiB variant isolates. Process `RssAnon` minus the a0 value recovers the known size within 0.02 MiB; the cgroup anon high-water recovers it as a slope (a256 - a16 = 240.0 MiB, known 240); `VmHWM` adds the program's resident file pages (about 1.4 MiB); `memory.peak` adds a container start-up charge of about 9.5 MiB that appears even for the 0 MiB program and is not sampled by the probe (it happens before the first sample). The a0 cgroup `anon` of 5.91 is container start-up anon sampled at the boundary of an empty workload (not itemised).

### Class b: the same plus a concurrent 256 MiB file write (standard, 30 + 3, A/A b64f256 vs copy)

`results/b/report.md`. The file is written to the container's overlay filesystem and stays in page cache (buffered).

| source | b64f256 | b256f256 | class a (64 / 256) | contamination of the source |
| --- | --- | --- | --- | --- |
| `cgroup_file_hwm_mib` | 256 | 256 | 0 | file size, exactly |
| `cgroup_peak_mib` | 331.1 | 523.7 | 73.42 / 265.7 | +257.7 / +258.0 over class a: peak = anon + file + start-up |
| `anon_settled_0s_mib` | 65.31 | 257.3 | 64.3 / 256.3 | +1.0 (writer thread's 1 MiB buffer) |
| `rssanon_settled_0s_mib` | 65.11 | 257.1 | 64.11 / 256.1 | +1.0 (same buffer) |
| `vmhwm_mib` | 66.67 | 258.7 | 65.43 / 257.4 | +1.2-1.3 (buffer and thread stack) |

A/A half-widths: `cgroup_peak_mib` 0.0082, `vmhwm_mib` 0.0006, `anon_settled_0s_mib` 0. File I/O moves the cgroup peak by the file size and leaves anon and `VmHWM` unchanged within the program's own 1 MiB buffer.

### Class c: glibc retention after multithreaded churn (standard, 20 invocations + 1 warm-up round per variant, A/A c6 vs c6-copy)

`results/c/report.md`. Churn with 12 threads for 5 s, then 126 s idle; windows 0 / 30 / 120 s sampled in the same block. Variants: cpuset 12 CPUs (6-11,18-23), 6 CPUs (6-11), 2 CPUs (6,7), `MALLOC_ARENA_MAX=2` at 6 CPUs, and the A/A duplicate of the 6-CPU variant. Pilot (`results/pilot/c`, 4 blocks each at 12 and 2 CPUs, excluded from inference) showed 413.7-416.8 MiB at every window and fixed the bad-mode threshold at 420 MiB (about 3 MiB above the pilot maximum, a tail rule).

| variant | `anon_settled_0s_mib` | `anon_settled_30s_mib` | `anon_settled_120s_mib` | ratio at 120 s vs c6 [95% CI] | bad_mode (0/30/120 s) | arenas |
| --- | --- | --- | --- | --- | --- | --- |
| c12 | 416.3 | 416.3 | 416.3 | 1.001 [0.9998, 1.002] no measurable difference | 0/20 each | 13 |
| c6 | 415.7 | 415.8 | 415.8 | baseline | 0/20 each | 13 |
| c2 | 414.9 | 414.9 | 415 | 0.9979 [0.9968, 0.9993] lower | 0/20 each | 13 |
| c6-arena2 | 387 | 387.2 | 387.9 | 0.9327 [0.9288, 0.9359] lower | 0/20 each | 2 |
| c6-copy (A/A) | 415.7 | 415.8 | 415.8 | 0.9999 [0.9988, 1.001] | 0/20 each | 13 |

A/A floor: ratio half-width 0.0010 at every window; rate difference interval half-width 0.161 (Newcombe), each rate's Clopper-Pearson upper bound 0.168 at 0/20. Other sources at 120 s (same report): `vmhwm_mib` c6 419.4 [419.3, 419.5]; `cgroup_peak_mib` 421.6 [421.5, 421.8]; `rssanon_settled_120s_mib` 415.5.

Findings: (1) this churn program does not release memory after the boundary — the 0, 30 and 120 s windows agree within 0.9 MiB at every condition, unlike the live daemon of the live-host investigation whose settled anon kept falling between 30 s and 120 s; (2) retention is unimodal here, so the bad-mode rate is 0/20 at every window and condition and distinguishes nothing at this threshold (20 blocks resolve a rate difference of about 0.16 from zero at best, per the A/A interval); (3) the CPU count moved the level by 0.2% or less (c2 -0.2%, c12 +0.1% of c6, both just outside the A/A half-width of 0.1%; a small effect, not an allocator mode change; 13 arenas at every cpuset); (4) capping arenas at 2 removed 7% (about 28 MiB) of retained anon; (5) `memory.peak` sits 6 MiB above `anon_settled`, `VmHWM` 3.6 MiB above (resident file pages),.

### Class d: probe overhead (standard, 30 + 3, A/A probe vs probe-copy)

`results/d/report.md`. The same `alloc --mib 64` program run bare (self-report only) and wrapped by the probe (interval 0.1 s).

| metric | bare | probe | ratio probe/bare [95% CI] | A/A half-width | verdict |
| --- | --- | --- | --- | --- | --- |
| `self_vmhwm_mib` | 65.46 | 65.45 | 0.9998 [0.9995, 1] | 0.00038 | no measurable difference |
| `self_cgroup_peak_mib` | 71.93 | 73.31 | 1.019 [1.016, 1.024] | 0.0042 | higher (worse) |

The probe does not change the measured process's own `VmHWM`; it adds about 1.4 MiB (1.9%) to the container's `memory.peak` (the probe shell and its helper processes; not itemised). CPU overhead of sampling was not measured.

## What each source counts

- `memory.peak`: anon plus page cache plus shared pages of the whole cgroup, including the container start-up charge (about 9.5 MiB here) and any probe; read-only inside a container (cannot be reset there) and removed with the container, so the probe reads it before exit. It is not a process number.
- `cgroup_anon_hwm_mib`: anon of every process in the cgroup (probe, wrappers), sampled, so it can miss a peak between samples (interval 0.5 s or 0.1 s here; the class a programs hold their allocation for 1 s).
- `cgroup_file_hwm_mib`: page cache charged to the cgroup, including written files.
- `VmHWM`: the process's resident peak, anon plus resident file-backed pages (about 1.4 MiB of binary and libc here), last sample before exit.
- `RssAnon`: the process's anon only.

## Limitations

- One host, one kernel, daytime live use; pinned but not fenced; CPU PSI maximum 39.5 during the batch.
- One build per variant: the layout-build part of R5 is not exercised (memory values here are deterministic to 0.01 MiB, but this is a deviation from the full protocol).
- The churn program is unimodal and does not release memory; it does not reproduce the live daemon's bimodal retention, so the bad-mode rate here is a demonstration of the metric and its resolution, not a measured mode rate. The threshold (420 MiB) comes from a 8-block pilot.
- The container start-up charge in `memory.peak` was inferred from the 0 MiB variant, not sampled directly.
- Only anonymous memory and buffered overlay-filesystem writes were calibrated: no shared memory, tmpfs, mmapped files, memory limits, swap or reclaim.
- Class c's CPU-count comparison used cpusets of 2, 6 and 12 CPUs on one CCD (SMT siblings are included in the 12-CPU set); with 12 worker threads the arena count was 13 everywhere.
- Heap profilers were not used.

## Setup (full environment)

- Host: Linux 7.2.12+deb13-amd64, cgroup v2 (`cgroup2fs`, controllers file present in the container), AMD Ryzen 9 7900X, 24 logical CPUs.
- Docker 29.9.3 (engine), build with `docker build -t memcal:1 memory-measurement-calibration` (network needed for `apt-get` in the builder stage); base image `debian:trixie-slim@sha256:f6b08b09a05725f9431502d3b5714f5c4576e82c1a84fa1debe0c24a7e0c3ec4`; in-image toolchain gcc (Debian 14.2.0-19) 14.2.0 and libc6-dev from Debian trixie (installed by apt, unpinned), flags `-O2 -pthread`; the runtime image has only the base, the two binaries and `gcc-version.txt`.
- Host tooling: bun 1.4.4 (runs `scripts/measure.mjs`, `gen-configs.mjs`, `scripts/render-index.mjs`), POSIX `sh` (dash) and coreutils; no other packages. The probe needs `awk`, `mktemp`, `mkfifo`, `sleep` (all in the Debian base image).
- Run from the repository root: `bun memory-measurement-calibration/gen-configs.mjs --bad-mib 420`, then for each class `bun scripts/measure.mjs run --config memory-measurement-calibration/configs/<class>.json --out memory-measurement-calibration/results/<class> --host <name>` and `bun scripts/measure.mjs report memory-measurement-calibration/results/<class>`. The recorded hostname in `results/*/env.json` was replaced by `measurement-host`.
- The configs run `run.sh` through `sh`; the class c cpuset is carried as `CAL_PIN` in the variant argv.
