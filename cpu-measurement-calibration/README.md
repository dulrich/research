# CPU measurement calibration: what each CPU source counts

A calibration of the CPU numbers a container run can produce — perf task-clock, the child's rusage user and system time, retired instructions and cycles (user and kernel mode), and the container cgroup's `cpu.stat` usage — against a fixed-work program at several sizes and a zero-work control, against first versus later runs in a container, against pinned versus unpinned placement, and against a busy or offline SMT sibling. All numbers come from the in-container probe `scripts/cpuprobe.sh` driven by `scripts/measure.mjs`; the tables below quote the generated `results/<class>/report.md`, `slopes.md` and `spread.md` files.

## Question

CPU-cost claims need to say which source they read and what that source counts. How much does each source add on top of the work (the intercept), how does it scale with work (the slope), is the first run in a container different, what do pinning and frequency do, and how much does a busy SMT sibling, or an idle versus an offline one, change CPU time and cycles?

Rigor: **standard** (`../methods/timing.md`: interleaved invocations, warm-up rounds, padded environment, A/A pair per class, hierarchical bootstrap, 30 invocations plus 3 warm-up rounds per variant), with stated exceptions: R1 in-process level (each invocation runs one fixed loop of N iterations, so there is no in-process repetition to allocate and no in-process warm-up; the fixed loop is the timed region), and R5 (each variant is one build of one program, so the report's "builds" column is 1 and layout variation is limited to environment padding). Pilots (R9; 6 invocations, 1 warm-up round) are under `results/pilot/` for a-desktop, b, c, d and e-lat; they chose the counts (A/A half-widths of task-clock at 6 invocations: 0.4-0.6% in desktop classes b and c, 5% in class a, whose zero-work and short cells add start-up noise, and 0.3-0.8% in the laptop classes) and are excluded from inference. Class a-laptop and e-thr have no pilot (same programs as their desktop or sibling classes). Every figure below that comes from a cross-run comparison says so. Host labelling per `../methods/live-host.md`: the 12-core desktop is live (its owner uses it) and classes a and b are pinned inside CCD1; class c's unpinned cells are **diagnostic exceptions to LH2** whose conclusions are limited to placement and frequency; the 2-core laptop is idle (outside the live-host scope).

## Method

- **Probe** (`../scripts/cpuprobe.sh`, POSIX sh): runs the command under one `perf stat --no-big-num -e task-clock,instructions:u,cycles:u -o FILE` (plus `:k` events with `--kernel`) and parses perf's default-mode output, which carries both the counters and the child's rusage "seconds user" / "seconds sys" lines (the CSV mode has no user/sys lines, so one default-mode run gives every source). It reads the cgroup `cpu.stat` `usage_usec` and the `/proc/stat` row of `--sibling CPU` just before and after the perf invocation. `cpuprobe.sh --help` lists the metrics: `cpu_task_clock_ms`, `cpu_user_ms`, `cpu_sys_ms`, `instructions_u`, `cycles_u`, `instructions_k`, `cycles_k`, `cgroup_usage_ms`, `sibling_busy`. Any unreadable source, refused counter, or unparseable line is an error on stderr and a nonzero exit with no MEASURE lines. A sibling that is offline (online file `0`, `/proc/stat` row absent) is reported as `sibling_busy 0` with a stderr note.
- **Program** (`src/work.c`): `work lat N` is one dependent LCG chain (one multiply-add per iteration, 4 cycles each), `work thr N` is four independent chains (multiplier-port bound; 5 instructions per iteration for lat, 11 for thr). `N = 0` is the zero-work control.
- **Run wrapper** (`run.sh`): one throwaway `docker run --rm` per invocation with `--cap-add PERFMON --cap-add SYS_ADMIN` (both hosts have `perf_event_paranoid=3`, see `../methods/timing.md` "Counters in Docker"), the probe mounted read-only. `probe` is one probe run in a fresh container; `later` runs the probe twice in the container and emits the second; `pair` emits both (`first_*`, `second_*`). `--antagonist CPU` starts a same-workload container pinned to that CPU before the measured container and removes it on every exit path. The container prints its effective cpuset (`Cpus_allowed_list`) as `cpuset_ncpus` and `cpus_allowed_list` (in `log.txt`). `offline-run.sh` records the online file of laptop cpu3, writes 0 through a privileged container, runs the config, and restores and reads back on every exit path.
- **Configs** (`configs/*.json`, generated by `gen-configs.mjs`): every metric has a `metrics` entry (level, lower is better). Laptop configs reach the host through the driver's ssh `channel` with `{host}` given on the command line; the recorded host name in each `env.json` was replaced by the class label afterwards (published-file rule). `analyze.mjs` computes the least-squares slopes and the per-variant ranges from `raw.jsonl`.
- **Classes:** (a) N = 0, 1e8, 3e8, 1e9 (latency mode), A/A on 3e8, on both hosts, pinned, with `--kernel`; (b) fresh container versus the second run in the same container, N = 3e8, desktop pinned to CPU 6; (c) desktop, pinned to CPU 6 versus unpinned, latency and throughput modes, N = 3e8; (d) laptop pinned to CPU 2, sibling CPU 3 idle versus a same-workload antagonist pinned to CPU 3, both modes, N = 3e8; (e) the same laptop cells with CPU 3 offline.

## Results

Hosts: the 12-core desktop (AMD Ryzen 9 7900X, SMT on, governor powersave with amd-pstate-epp, boost on, kernel 7.2.12, load average 3-6 on 24 CPUs during the runs), and the 2-core laptop (Intel Core i7-5600U, 4 threads: siblings 0-1 and 2-3, governor schedutil, kernel 6.12.116, load average 0.3-2.0 from its own runs). Docker 29.9.3 on both. All numbers below are standard rigor unless stated; medians with the report's 95% interval; ratios are against the class baseline.

### Class a: source agreement and control subtraction (standard, 30 + 3 per variant, A/A n3e8 vs n3e8-copy)

`results/a-desktop/report.md`, `results/a-laptop/report.md`; fits in `results/a-*/slopes.md` (ordinary least squares over all 120 recorded invocations of the four sizes plus the copy, slope per 1e8 loop iterations). "N=0 median" is each source's intercept: what a run that does no work reports.

| source | desktop N=0 median | desktop slope per 1e8 | laptop N=0 median | laptop slope per 1e8 |
| --- | --- | --- | --- | --- |
| `cpu_task_clock_ms` | 0.34 ms | 74.81 ms (R^2 0.99996) | 0.325 ms | 125.8 ms (R^2 0.999994) |
| `cpu_user_ms` (rusage) | 0.487 ms | 74.77 ms | 0.84 ms | 125.7 ms |
| `cpu_sys_ms` (rusage) | 0 | 0.04 ms (R^2 0.02: no trend) | 0 | 0.008 ms (no trend) |
| `instructions_u` | 102,900 | 5.000e8 (exactly 5 per iteration) | 107,900 | 5.000e8 |
| `cycles_u` | 147,300 | 4.001e8 | 234,500 | 4.002e8 |
| `instructions_k` | 1.88e6 | 1.95e5 (R^2 0.69) | 5.01e5 | 1.82e5 (R^2 0.99) |
| `cycles_k` | 1.63e6 | 4.85e5 (R^2 0.69) | 6.75e5 | 2.34e5 (R^2 0.94) |
| `cgroup_usage_ms` | 10.85 ms | 74.85 ms | 17.86 ms | 125.7 ms |

- `instructions_u` is linear in N to the last digit and `cycles_u` is 4 per iteration (the chain's latency); their intercepts are the process start-up (1e5 instructions, 1.5e5-2.3e5 cycles) and do not move with work.
- Task-clock and rusage user time agree on the slope (74.8 and 74.77 ms per 1e8 on the desktop; 125.8 and 125.7 on the laptop); the intercepts differ by 0.15-0.5 ms.
- The cgroup `usage_usec` delta carries a fixed charge that is not workload cost: **10.5 ms** (desktop: 10.85 minus the 0.34 ms task-clock) and **17.5 ms** (laptop), which is 4.6% and 4.5% of the 3e8 run and is perf's and the shell's own start-up. Its slope matches task-clock (74.85 and 125.7 ms), so the attributable cost is the slope or the control-subtracted value (n3e8 minus n0), never the raw total.
- Kernel-mode counters are dominated by their intercept (start-up, exec, page faults: 1.9e6 instructions on the desktop against 1.95e5 per 1e8 iterations); their slope tracks timer interrupts, so they are not a cost metric for the loop.
- `cpu_sys_ms` is zero at the control and shows no trend with work (sub-millisecond system time is below rusage's resolution here).
- A/A half-widths on task-clock: 0.11% (desktop), 0.08% (laptop).

### Class b: first invocation in a fresh container versus a later one (standard, 30 + 3, A/A fresh vs fresh-copy)

`results/b/report.md`, desktop pinned to CPU 6, N = 3e8 latency mode. The treatment is a measured condition of the variant (`later` runs the probe twice in one container and emits the second; `pair` emits both), not the driver's discarded warm-up rounds.

| metric | fresh | later (second run, same container) | ratio later / fresh [95% CI] | A/A half-width | verdict |
| --- | --- | --- | --- | --- | --- |
| `cpu_task_clock_ms` | 223.5 | 223.4 | 0.9996 [0.998, 1] | 0.0018 | no measurable difference |
| `cycles_u` | 1.200e9 | 1.200e9 | 1 [1, 1] | 0.00002 | no measurable difference |
| `instructions_u` | 1.500e9 | 1.500e9 | 1 [1, 1] | 3.5e-9 | no measurable difference |
| `cgroup_usage_ms` | 234.0 | 232.8 | 0.9945 [0.9929, 0.9957] | 0.0018 | lower (1.2 ms) |

The `pair` variant (first and second run in the same container) gives medians 223.6 / 223.4 ms task-clock and 234.3 / 232.7 ms cgroup usage (`results/b/spread.md`). On a quiet pinned core with a 0.22 s workload, the first run is not measurably slower in task-clock, cycles or instructions; the only difference is about 1.2 ms of cgroup CPU (cold start-up of the shell and perf paths), which is part of the cgroup's fixed charge from class a. An earlier indicative spike saw the first run 1-3% slower; that is not reproduced here.

### Class c: placement and frequency, 12-core desktop, live (standard, 30 + 3, A/A pinned vs pinned-copy) — diagnostic exceptions to LH2

`results/c-lat/report.md`, `results/c-thr/report.md`, `results/c-*/spread.md`. Pinned: `--cpuset-cpus 6` (CCD1); unpinned: no cpuset (24 CPUs, `cpuset_ncpus` 24, recorded per invocation with `cpus_allowed_list` in `log.txt`). `sibling_busy` is that of CPU 18, the sibling of CPU 6 (for the unpinned cells it only indicates host load on that CPU). Conclusions limited to placement and frequency.

| mode | `cpu_task_clock_ms` pinned | unpinned | ratio unpinned / pinned [95% CI] | A/A half-width | `cycles_u` ratio [95% CI] |
| --- | --- | --- | --- | --- | --- |
| latency | 223.5 | 218.6 | 0.9781 [0.9755, 0.9797] | 0.0015 | 1 [1, 1] |
| throughput | 225.4 | 219.5 | 0.9741 [0.9706, 0.9775] | 0.0004 | 1.001 [1.001, 1.001] |

Unpinned runs were 2.2-2.6% faster in task-clock with identical cycles (about 5.37 GHz pinned, 5.49 GHz unpinned from cycles over task-clock): the difference is frequency of the CPUs the scheduler picked, not work. `instructions_u` per invocation was identical to within 1e-5 percent in every cell.

Stability under day load (`spread.md`, range = (max - min) / median over 30 recorded invocations):

| cell | `instructions_u` range | `cycles_u` range | `cpu_task_clock_ms` range | max `sibling_busy` |
| --- | --- | --- | --- | --- |
| pinned-lat | 5e-6% | 0.20% | 1.87% | 0.08 |
| pinned-lat-copy | 4e-6% | 0.019% | 1.06% | 0.04 |
| unpinned-lat | 5e-6% | 0.039% | 3.03% | 0.08 |
| pinned-thr | 1e-6% | 0.092% | 2.01% | 0 |
| pinned-thr-copy | 2e-6% | 17.6% | 25.5% | 0.93 |
| unpinned-thr | 3e-6% | 3.41% | 10.9% | 0.72 |

Instruction counts did not move at all while task-clock ranged up to 25.5% in cells where another task shared the SMT sibling (pinned-thr-copy: one invocation saw `sibling_busy` 0.93, with cycles +17.6% and task-clock +25.5% over the median). Instruction counts are the contention-independent cost metric; task-clock and cycles of throughput-bound code are not.

### Class d: SMT sibling idle versus busy, 2-core laptop, idle (standard, 30 + 3, A/A idle vs idle-copy)

`results/d-lat/report.md`, `results/d-thr/report.md`. Pinned to CPU 2; busy means a same-workload antagonist container pinned to CPU 3 running for the whole invocation (`sibling_busy` 1 in every busy cell, 0 in the idle cells, median).

| mode | `cpu_task_clock_ms` idle | busy | ratio busy / idle [95% CI] | `cycles_u` ratio [95% CI] | `instructions_u` | A/A half-width (task-clock) |
| --- | --- | --- | --- | --- | --- | --- |
| latency | 378.1 | 379.2 | 1.003 [1.001, 1.004] | 1 [1, 1] | 1.500e9 both | 0.0009 |
| throughput | 379.2 | 785.2 | 2.071 [2.069, 2.075] | 2.068 [2.066, 2.071] | 3.300e9 both | 0.0021 |

A busy sibling doubled CPU time and cycles of the throughput-bound program (rusage user time 2.075x) and moved the latency-bound one by +0.3% (+1.1 ms; its cycles did not move). Instructions are identical in all cells.

### Class e: sibling offline versus idle, 2-core laptop (standard, 30 + 3, A/A offline vs offline-copy)

`results/e-lat/report.md`, `results/e-thr/report.md`. Laptop cpu3 offline (`pinned_cpu_online` 0 in the env record; the probe printed `sibling_busy 0` and the `sibling offline` note in every invocation). The offline and idle conditions cannot be interleaved (the host state is one setting per run), so the comparison with class d's idle cells is **cross-run** (indicative; same day, same image and program, different time).

| mode | `cpu_task_clock_ms` offline | idle (class d: variant / copy) | `cycles_u` offline | `cycles_u` idle | `cycles_u` range offline / idle |
| --- | --- | --- | --- | --- | --- |
| latency | 379.1 [378.9, 379.6] | 378.1 / 378.0 | 1.201e9 | 1.201e9 | 0.017% / 0.18% |
| throughput | 378.9 [378.8, 379.3] | 379.2 / 378.8 | 1.201e9 | 1.203e9 | 0.014% / 0.82% |

"Idle" is equivalent to "offline" within 0.3% in task-clock (+0.27% latency, -0.08% throughput) and within 0.17% in cycles; the only systematic difference is that offline cells had much narrower cycle ranges (0.014-0.025% against 0.18-0.82% for idle), because an idle sibling still takes occasional background work and an offline one cannot. The laptop's cpu3 read back `1` (online) after both class-e runs (the readback lines are in `notes.md`).

## Setup and dependencies

- Host tools: bun 1.4.4 (runs `scripts/measure.mjs` and the folder's `gen-configs.mjs` / `analyze.mjs`; no packages), Docker 29.9.3, `ssh` with BatchMode key login for the laptop, cgroup v2, `perf_event_paranoid=3` (counters work only with `--cap-add PERFMON --cap-add SYS_ADMIN` on the throwaway bench container).
- Image: `docker build -t cpucal:1 cpu-measurement-calibration`. `debian:trixie-slim` pinned by digest (`sha256:f6b08b09a05725f9431502d3b5714f5c4576e82c1a84fa1debe0c24a7e0c3ec4`); build stage `gcc` 14.2.0 with `libc6-dev` compiles `src/work.c` with `-O2`; runtime stage `linux-perf` (perf 6.12.117). The probe needs POSIX `sh`, `awk`, `sed`, `mktemp` (all in the image) and `perf`.
- Laptop: `docker save cpucal:1 | ssh HOST docker load`; copy `run.sh` to `/var/tmp/cpucal/cpu-measurement-calibration/` and `scripts/cpuprobe.sh` to `/var/tmp/cpucal/scripts/` on the laptop (the shell guard needs the folder name in the path); remove both at the end. Class e needs a privileged container to write `/sys/devices/system/cpu/cpu3/online` (done by `offline-run.sh`, which restores and reads back).
- Reproduce: `bun cpu-measurement-calibration/gen-configs.mjs`, then for each desktop config `bun scripts/measure.mjs run --config cpu-measurement-calibration/configs/<class>.json --out cpu-measurement-calibration/results/<class>`, for laptop classes a-laptop, d-lat, d-thr the same plus `--host HOST`, for e-lat/e-thr `sh cpu-measurement-calibration/offline-run.sh HOST 3 cpu-measurement-calibration/configs/<class>.json cpu-measurement-calibration/results/<class>`; then `bun scripts/measure.mjs report <dir>` and `bun cpu-measurement-calibration/analyze.mjs slope|spread <dir>`.
- Time: about 35 minutes of runs in total.
