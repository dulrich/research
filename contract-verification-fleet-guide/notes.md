# Contract verification in the fleet: working notes

A working log for the investigation. Each step appends a dated entry: what was tried, what was learned.

## 2026-11-18 — feasibility check and tool survey

### Feasibility check (measured before the survey)

In a container built from the official `rust:1.99.1-slim-trixie` image with the Verus release `0.2026.10.04.426d8b0` (the release the `jpeg2000_rs` CI pins) and the Rust toolchain that release requires, `1.98.1`:

- the article's fixed Brotli header twin plus a twin of a 4-byte length-prefix cap check verified (`verification results:: 4 verified, 0 errors`);
- the article's historical subtraction was rejected (`error: possible arithmetic underflow/overflow`, `1 verified, 1 errors`);
- a hand-written twin of the `crucible-dev-env` login state machine (`crates/crucible-greetd/src/machine.rs`, with `String` and `Vec<String>` fields) verified the contract "a start-session request is emitted only from the authenticating state on a success reply" (`4 verified, 0 errors`);
- two frictions: this release requires `final(self)` (or `old(self)`) around a `&mut self` parameter in a postcondition, with a migration note upstream (`source/docs/migration-mut-ref.md` in the Verus repository); and with a conjunct that the emitted command list equals the machine's stored list (the value comes from `Vec<String>::clone`) the postcondition failed, and it verified with that conjunct removed. The cause was not investigated.

The host had no Verus installed; Verus pins its own Rust toolchain.

The rest of the 7,000-plus-line `PROOFS.md` and of `specs/` was sampled, not read.

### What was learned

- The article's Brotli examples are twins, but `jpeg2000_rs` is the other shape: contracts attached to the production source. One source tree serves two builds. Under plain Cargo the contracts are cfg-ed out; under the Verus frontend the `verus_keep_ghost` configuration turns them on. The models and proof support are separate trees (`specs/`, `proofs/`) mounted into the crate only under that configuration.
- The proof-to-code ratio in `jpeg2000_rs` is large: `specs/` holds 74,361 lines against 110,470 non-test lines under `src/` (which itself carries the in-source contracts, and 75,113 more lines in test files), and `proofs/` adds 8,685. A reader sizing adoption from the article's four-byte header example will underestimate this.
- The project's own documents are blunter about limits than the article: no complete bytes-to-image proof, model-to-standard review outstanding, source-function coverage recorded as "not measured", lifetime analysis disabled with `--no-lifetime`, and the verifier, solver and standard-library specifications named as part of the trusted base.
- The project's gate rejects `external_body`, `assume`, `admit`, `assume_specification` and similar escapes in the verified source. The three occurrences of `axiom_`-prefixed names in the source are calls to library lemmas, not new axioms (reading; not checked by running the gate).
- Kani, Creusot, Prusti, Flux, Aeneas and hax were not installed or read from a local source. Their rows in the survey are from documentation or general knowledge and say so.

### The contracts in plain words

- **C1 (greetd frame bound, `crucible-greetd/src/codec.rs:152` `read_message`).** For every input stream: a 4-byte length prefix is read; the announced length is accepted exactly when it is at most `MAX_MESSAGE_LEN` (65,536); an accepted length is exactly the number of body bytes requested next, and the body returned is those bytes; on rejection by the cap only the 4-byte header was requested and no body buffer was allocated. Also checked: the survey's writer/reader agreement, "anything `write_message` accepts, `read_message` accepts".
- **C2 (login state machine, `crucible-greetd/src/machine.rs:109` `handle`, `:142` `on_auth_response`).** A `StartSession` request is emitted only from `Authenticating` on a `Success` reply, and the machine is then `Starting`; the `StartSession` carries the configured command (element-wise equal, see the clone note below); `Done` is entered only from `Starting` on `Success`; a `PostAuthMessageResponse` with `Some` answer is emitted only from `Prompt` on `Submit`, carrying exactly the submitted secret; an event with no match arm (the `_ => self.out(None)` arm) emits no request and leaves the state and the message line unchanged; `cmd` is never changed. `on_auth_response`, called only in `Authenticating`, moves to `Starting` exactly on `Success`, never to `Done`, never emits an answer.
- **C3 (descriptor ranges, `crucible-login/src/worker/spawn.rs:103` `close_ranges`).** For every `keep: Option<i32>` the result equals a model; about the model it is proved that no range contains 0, 1, 2 or the kept descriptor (when it is at least 3), and every other descriptor from 3 to `u32::MAX` is in exactly one range. Every cast and subtraction or addition in the function is checked for overflow by the verifier (Verus checks arithmetic in executable code by default).
- **C4 (worker request ordering, `crucible-login/src/worker/process.rs:125` `serve`, `:181` `serve_open`, `:61` `teardown_for`).** In a model where PAM and the fork return arbitrary results and every effect is appended to a ghost event log: every spawn attempt and the spawned user process come after a successful `pam_open_session` in the log; a spawned user process is the last event (at most one); the phase never moves backwards in `serve_open`; what the phase claims (credentials established, session opened) is backed by the log; `teardown_for` gives `close_session ==> delete_cred`, `delete_cred` exactly when the phase is past `Authenticated`, and `close_session` exactly when it is `Opened`.

C5 (`recv_flags`, survey G3) was not attempted.

### Obstacles, with reproductions

Each reproduction is in `pilot/obstacles/` and is run by the pilot command, which checks that the named error still appears.

- **O1, C1 on the real source: generic I/O.** `read_message` is generic over `R: Read` and calls `Read::read_exact`, decodes with `u32::from_ne_bytes`, and wraps `io::Error`; vstd specifies none of them. Reproduction: `obstacles/read_message_generic_reader.rs` (the real body with the JSON decode cut). Verifier: `` error: `core::io::error::Error` is not supported ``, `` error: `std::io::Read::read_exact` is not supported ``, `` error: `core::num::impl&%8::from_ne_bytes` is not supported ``. Stating C1 on the real function would need assumed specifications for all three (and for `serde_json::from_slice`), making the proof conditional on them; it was not done, so C1 has no real-source artifact.
- **O2, C2: derived `Clone` without a specification.** A derived `Clone` on an enum with a `String` field gets no specification (`warning: autoderive Clone impl does not take the form Verus expects; continuing, but without adding a specification for the derived Clone impl`), so after `self.state.clone()` the verifier knows nothing about the value matched on. Reproduction: `obstacles/derived_clone_no_spec.rs` (`error: assertion failed`, `2 verified, 1 errors`). Writing `assume_specification` for it directly fails (`error: duplicate specification for this trait method implementation`); the in-source diff marks the derive external (`verifier::external_derive(Clone)`) and then assumes `ensures r == *s`. That assumption is the one trusted statement in the C2 real-source proof.
- **O3, C2: private fields in a public contract.** A postcondition of the public `handle` cannot name the private `state` field (`error: disallowed: field expression for an opaque datatype`). Reproduction: `obstacles/private_field_in_public_contract.rs`. Workaround in the diff: `pub closed spec fn` accessors (`spec_state`, `spec_message`, `spec_cmd`).
- **O4, the feasibility check's failed `cmd` conjunct: `Vec` equality after `clone`.** Cause found: after `Vec::clone`, vstd gives equality of the views (`r@ == v@`), not of the vectors (`r == *v`); this holds for `Vec<u8>` as much as for `Vec<String>`, so it is not about `String`. `String::clone` does give `==` in this release (checked in a scratch run). Reproduction: `obstacles/vec_clone_equality.rs` (`2 verified, 2 errors`: the two `r == *v` postconditions fail, the `r@ == v@` one verifies). The way to state it that verifies: compare views, `cmd@ == pre.cmd@` (in-source, where the module's own `View` struct shadows vstd's `View` trait, written `vstd::view::View::view(&cmd) == ...`).
- **O5, C4 on the real source: the `Pam` handle and socket I/O.** `serve` takes `&mut Pam` (an FFI handle whose methods call `libpam`), receives requests with `recv_req` (a `recvmsg` wrapper with `SCM_RIGHTS`), replies through `send`, and `serve_open` runs a closure with `?` over `PamError`. Stating the ordering on it needs a specification of every `Pam` method used (what a success or failure means for the phase) and of the socket calls, all assumed. No reproduction file: the blocker is the volume of assumed specifications, not a single verifier error; the twin is the model.
- Smaller frictions, not obstacles: inside `machine.rs` the crate's `View` struct shadows vstd's `View` trait, so `x@` does not resolve and the view has to be written out; `on_auth_response` needed a precondition (`Authenticating`) because, as a standalone function, its info/error arm keeps whatever state it was called in; `#[verus_verify]` on the whole `impl LoginMachine` clashes with per-function `verus_spec` (`error: Multiple #[verus_spec] attributes are not allowed`), so attributes go on each function; `matches` with `&&` must be parenthesised in clauses; a returned-value name that equals a parameter name (`r` in `read_message(r: &mut R)`) is an error.

### What the in-source diffs change

- `in-source/c3-close-ranges.diff` (53 lines added, none removed): a `#[cfg(verus_keep_ghost)] use vstd::prelude::*;`, a `#[cfg(verus_keep_ghost)] verus! { ... }` block with the model and the lemma, one `#[cfg_attr(verus_keep_ghost, verus_spec(...))]` on `close_ranges`, and two marker comments. The function body is unchanged.
- `in-source/c2-machine.diff` (117 lines added, 10 removed, in `codec.rs` and `machine.rs`): 32 of the added lines are build plumbing (serde derives and attributes moved under `cfg_attr(not(verus_keep_ghost), ...)`, `CodecError`, `write_message` and `read_message` and the serde import under `#[cfg(not(verus_keep_ghost))]`, `verus_verify` on each type); the rest are the contract, the spec accessors, the clone assumption and `external_body` markers. The 10 removed lines are the original derive and serde attribute lines, re-added in gated form. No executable statement changed.
- Neither diff was built with plain Cargo in this pilot, so whether the gated source still compiles and passes its tests unchanged under Cargo was not checked; under Cargo an unknown `verus_keep_ghost` cfg would also raise `unexpected_cfgs` warnings unless declared. Verification ran on a harness, not on the crate: for C2 the harness includes the patched `codec.rs` and `machine.rs` byte for byte as modules (without `lib.rs` and `fake.rs`); for C3 it includes only the marked region of `spawn.rs`. A whole-crate run with `cargo verus` would also need `vstd` as a dependency and was not attempted.

### What each proof assumes and does not establish

- **C1 twin.** Assumes the twin is faithful (fidelity checked by reading the real `read_message` beside it, and the real crate's `rejects_oversize_length` test covers one oversize length, consistent with the twin); assumes `read_exact` either fills the buffer or fails. Does not establish anything about the real `R: Read` implementations, about `serde_json` decoding, or about the real function's code (the real function was not verified).
- **C2.** On the real source: assumes the derived `State::clone` returns an equal value; `view` and `new` are trusted and unverified, so nothing is proved about what the view shows (in particular not "the view never carries the answer"); `Secret`'s wipe-on-drop is not touched. Proves the listed obligations for every state and every event, for the real bodies of `handle`, `on_auth_response`, `cancel` and `out` as patched (unchanged statements). Does not establish anything about `Session::feed` (the I/O loop that sends the requests), about the greetd peer, or about liveness.
- **C3.** On the real source: assumes `RawFd` is `i32`. Proves the ranges for every `Option<i32>`, including negative values (a negative `keep` closes everything from 3, as the code does). Does not establish what `close_range(2)` does with the ranges (the `libc::syscall` in `close_all` is outside the proof).
- **C4 twin.** Assumes the twin's abstraction of `serve` (fidelity checked by reading the real match arms side by side; there is no direct test of `serve` in the repository, as the survey noted). Proves the ordering of the ghost log for every request sequence and every PAM and fork outcome. Does not establish anything about the real `serve`, about `recv_req` or the replies, about which account the process runs as, or about whether a second `pam_setcred(ESTABLISH)` after a failed `pam_open_session` is harmless (the survey's open question; the twin allows that path, as the code does).
- Twins are checked against the real code by reading, which is a human judgement, not a mechanical check; the twin files list every known difference in their header comments.

### Defects and specification gaps found in the target

- **Writer/reader disagreement (survey G1, confirmed).** `write_message` accepts any body whose length fits a `u32`; `read_message` refuses lengths above 65,536. The twin proves both sides: within the cap they agree (`writer_reader_agree_within_cap` verifies), and for every body of length 65,537 to 4,294,967,295 the frame the writer emits is refused by the reader (`writer_reader_disagree_above_cap` verifies). The survey's statement as written is rejected (finding diff). Counterexample class: any message whose JSON body is longer than 65,536 bytes. Whether the greeter can produce such a message (for example a `start_session` with a very long command, or a long PAM message from greetd) was not determined. Reported, not fixed.
- **`Starting` plus `AuthMessage` (survey G2) is consistent with the contract.** In `Starting`, an `AuthMessage` reply has no match arm, so the machine emits nothing and stays in `Starting`; the verified no-arm conjunct states exactly that. Whether that is the intended behaviour (it looks like a stuck state) is a question for the owner, not a contract violation.
- No other defect was found.

### Routes

- **C1, C2: real crate by path.** A harness crate (`pilot/kani/harness/`) depends on the staged `crucible-greetd` by path and calls only its public API: `codec::read_message`, `CodecError`, `MAX_MESSAGE_LEN`, `LoginMachine::new`, `handle`, `state`, `view`. - **C3, C4: in-source harness diffs.** `close_ranges` and `teardown_for` sit in the private modules `worker::spawn` and `worker::process`, so no outside crate can call them. `pilot/kani/in-source/c3-close-ranges.diff` (28 lines added, none removed) and `c4-teardown.diff` (33 added, none removed) only append a `#[cfg(kani)] mod kani_proofs` at the end of each file. No non-test code changes.
- **Stubbing in C1.** Without stubs, `c1_reject_above_cap` was still in symbolic execution of `serde_json` and the float-parsing code under it (`core::num::imp::bignum`) when the 600 s limit ran out. CBMC does not drop the decode path just because its guard (`len <= cap` together with `len > cap`) can never be true. The three symbolic C1 harnesses therefore replace `serde_json::from_slice` with `#[kani::stub]` (`-Z stubbing`) by a function that hits `unreachable!`, so the run also checks that the decoder is never reached on those paths. That was the second attempt. `c1_concrete_frame_decodes` runs the real `serde_json` on one concrete frame (`null`, `T = ()`) and does not use the stub.
