# CPU-usage measurement standard

This is the method every CPU-usage claim in this repository follows: the CPU time a process or container consumed, the instructions and cycles it retired, and how SMT siblings, placement and frequency move those numbers. It extends [timing.md](timing.md), whose rules R1-R11 (repetition, warm-up, interleaving, padding, bootstrap CIs, A/A floor, claim rule, fixed sample size, counters over the timed region, environment record) apply to CPU metrics unchanged, and [live-host.md](live-host.md) when the host is a live workstation. What it adds is which CPU source answers which question, what each source counts beyond the workload, and the SMT and placement effects that move a CPU number without the work changing. Rules are numbered C1, C2, ...; each has a one-line reason and a citation. The evidence is the calibration in [cpu-measurement-calibration](../cpu-measurement-calibration/) (classes a-e on a 12-core live desktop and a 2-core idle laptop, standard rigor with stated R1 in-process and R5 exceptions).

## Scope: rigor follows use

The two levels of [timing.md](timing.md) (Scope) apply as written. **Indicative** CPU numbers (sizing, a spike, a sanity check) are a few runs reported with the label *indicative*, the source and the command; they never carry a precise ratio or a "uses N% less CPU" claim. **Standard** is this document's rules C1-C9 on top of timing.md's R1-R11 and both reporting checklists, run through `scripts/measure.mjs` with `scripts/cpuprobe.sh`; it is required whenever CPU cost is the product of the research or the claimed separation is small against the run-to-run spread or against the fixed charges of C2. Every reported CPU number states its rigor level and its source.

## Rules

**C1. Name the question, then the source.** *CPU time of the process*: perf task-clock (`cpu_task_clock_ms`) or rusage user plus system time (`cpu_user_ms` + `cpu_sys_ms`). *CPU time of a container*: the cgroup `cpu.stat` `usage_usec` delta (`cgroup_usage_ms`), only with a zero-work control (C2). *Contention- and frequency-independent cost*: retired user-mode instructions (`instructions_u`). *Frequency and SMT effects*: user-mode cycles (`cycles_u`) read against task-clock (C6). Reason: task-clock and rusage user time agree on the slope (74.81 / 74.77 ms per 1e8 iterations desktop, 125.8 / 125.7 laptop), `instructions_u` is exactly 5 per iteration and `cycles_u` 4 per iteration, while the cgroup carries a fixed charge the others do not. Citation: calibration class a table (`results/a-desktop/slopes.md`, `results/a-laptop/slopes.md`); `perf-stat(1)`; kernel `Documentation/admin-guide/cgroup-v2.rst` (`cpu.stat`).

**C2. Raw whole-process totals are diagnostic; attributed cost is control-subtracted or a slope, for every source.** Every whole-process source (rusage, task-clock, counters, cgroup) counts process start-up as well as the workload. Workload-attributed cost is the value minus a matching setup-only or zero-work control, or the slope over known work sizes, consistent with [timing.md](timing.md) R10. For the cgroup this is mandatory: its delta carries a fixed charge over task-clock of **10.5 ms** (desktop) and **17.5 ms** (laptop), perf's and the shell's own start-up, 4.6% and 4.5% of a 0.22-0.38 s run. Reason: at N = 0 the sources report 0.34 ms task-clock, 1.0e5 instructions and 10.85 ms cgroup usage on the desktop, none of which is work; the cgroup slope (74.85 ms per 1e8) matches task-clock, so the slope and the control-subtracted value recover the work and the raw total does not. Citation: calibration class a ("N=0 median" and slope columns); timing.md R10.

**C3. Take the user/kernel split from rusage or from perf `:u`/`:k` counters, never from the cgroup split.** The cgroup `cpu.stat` `user_usec` / `system_usec` split was not calibrated (the probe does not emit it). In the kernel, both that split and rusage's are derived from the scheduler's precise total runtime apportioned by tick-sampled user/system accounting (`cputime_adjust()` in `kernel/sched/cputime.c`), unless the kernel uses virtual (full dynticks) CPU-time accounting; on a short run the split therefore has tick resolution. The standard reads system time from rusage (`cpu_sys_ms`, calibrated) and, when mode matters at finer resolution, from the perf `:k` counters (`instructions_k`, `cycles_k`, `--kernel`); kernel-mode counters are dominated by start-up and are not a cost metric for user code. Reason: `cpu_sys_ms` was 0 at the control with no trend over work (R^2 0.02) and jumped in steps of about 4 ms (one tick) when it was nonzero, while `instructions_k` at N = 0 (1.88e6) outweighed its per-1e8 slope (1.95e5). Citation: calibration class a table; `results/c-thr/spread.md` (`cpu_sys_ms` 0 / 4.03 ms); Linux `kernel/sched/cputime.c` (`cputime_adjust`); kernel `Documentation/timers/no_hz.rst` (full dynticks CPU-time accounting).

**C4. Record the SMT sibling's state; time and cycles claims on throughput-bound code need the sibling idle or offline.** Pass `--sibling CPU` (the measured CPU's SMT sibling) and report `sibling_busy`. A task-clock or cycles claim on throughput-bound code holds only with the sibling idle (`sibling_busy` about 0) or offline; instruction counts hold either way. Reason: a busy same-workload sibling made the throughput-bound program 2.071x [2.069, 2.075] slower in task-clock and 2.068x in cycles, and the latency-bound one only 1.003x, with identical instructions (class d); with the sibling offline, task-clock matched idle within 0.3% and cycles within 0.17%, with narrower cycle ranges offline (0.014-0.025% against 0.18-0.82%) — a cross-run comparison, so indicative (class e). Citation: calibration classes d and e (`results/d-thr/report.md`, `results/e-*/report.md`, `spread.md`).

**C5. Report the placement; ordinary claims follow LH2.** State the requested and the effective cpuset (`Cpus_allowed_list`) with every CPU-time number, and compare only within one placement. Pin and fence per [live-host.md](live-host.md) LH2; the calibration's unpinned cells were diagnostic exceptions to LH2 whose conclusions are limited to placement and frequency. Reason: unpinned runs were 2.2-2.6% faster in task-clock than pinned on the desktop (0.9781 [0.9755, 0.9797] latency, 0.9741 [0.9706, 0.9775] throughput) at equal cycles, because the scheduler picked faster-clocked CPUs. Citation: calibration class c table (`results/c-lat/report.md`, `results/c-thr/report.md`); live-host.md LH2, LH4.

**C6. Separate work from frequency with cycles over task-clock.** When task-clock moves, check `cycles_u`: equal cycles at different task-clock is a frequency or placement effect, more cycles at equal instructions is contention (SMT, cache); report which. Reason: class c's 2-3% task-clock change came with cycles ratio 1 [1, 1] (about 5.37 against 5.49 GHz), while class d's SMT slowdown moved cycles by the same 2.07x as task-clock. Citation: calibration classes c and d; `perf-stat(1)`.

**C7. On a live host, instruction counts are the stable cost; task-clock needs the sibling recorded.** Under day load `instructions_u` spread is negligible while task-clock spread reaches 25% when another task shares the sibling; live-host acceptability per class is [live-host.md](live-host.md)'s table, not restated here. Reason: across 30 invocations per cell `instructions_u` ranged by at most 5e-6% while `cpu_task_clock_ms` ranged up to 25.5% (pinned-thr-copy, one invocation at `sibling_busy` 0.93). Citation: calibration class c stability table (`results/c-*/spread.md`); live-host.md "When a live host is acceptable, per class".

**C8. Warm-up follows R2; no extra fresh-container penalty was found.** Discard warm-up per [timing.md](timing.md) R2. For a CPU-bound workload in a fresh container, the calibration found no first-run penalty in task-clock, cycles or instructions beyond R2, only about 1.2 ms of extra cgroup charge, which C2's control removes; an earlier indicative observation of a 1-3% first-run penalty was not reproduced, and the calibration wins. Reason: second run over first 0.9996 [0.998, 1] in task-clock, 1 [1, 1] in cycles and instructions, 0.9945 [0.9929, 0.9957] in cgroup usage. Citation: calibration class b (`results/b/report.md`, `results/b/spread.md`); timing.md R2.

**C9. Use the probe's metric names, and give every CPU metric a driver `metrics` entry.** `scripts/cpuprobe.sh` runs the command under one `perf stat` and prints `cpu_task_clock_ms`, `cpu_user_ms`, `cpu_sys_ms`, `instructions_u`, `cycles_u`, `cgroup_usage_ms`, plus `instructions_k` / `cycles_k` with `--kernel` and `sibling_busy` with `--sibling CPU`, exactly as `cpuprobe.sh --help` lists them. It is fail-closed: a missing perf, a refused or unparseable counter, a missing user/sys line or an unreadable `cpu.stat` is a stderr message and a nonzero exit with no MEASURE lines, so a partial record never enters the driver; an offline sibling is a valid `sibling_busy 0` with a stderr note. In the `measure.mjs` config each metric gets `{ "kind": "level", "better": "lower" }`. Counter access in Docker follows [timing.md](timing.md) "Counters in Docker" (`--cap-add PERFMON --cap-add SYS_ADMIN` at `perf_event_paranoid=3`). Reason: a metric without an entry is treated as a time and its verdicts read "faster"/"slower"; fixed names keep reports comparable across investigations. Citation: `cpuprobe.sh --help`; calibration Method (every config metric has an entry); timing.md "Using the driver".

## Reporting checklist (in addition to timing.md's)

An investigation README with a CPU-usage claim states:

- Rigor level (Scope) and, per metric, its source (task-clock, rusage, `instructions_u`, `cycles_u`, cgroup) and the question it answers (C1).
- Whether each number is a raw total (diagnostic) or attributed cost, and the control or the size slope used (C2).
- Where a user/kernel split is reported, its source (rusage or perf `:k`) (C3).
- The sibling CPU, `sibling_busy`, and whether the workload is latency- or throughput-bound (C4).
- Requested and effective cpuset, and any LH2 exception (C5); frequency settings and the cycles-over-task-clock reading where task-clock moved (C6).
- Host load class per live-host.md (C7) and warm-up handling (C8).
- The driver `metrics` map and the probe flags used (C9).
- Deviations from C1-C9 and why.
