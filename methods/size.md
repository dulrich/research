# Binary-size measurement standard

This is the method every artifact-size claim in this repository follows: the bytes of a built binary, its compressed (transfer) size, its mapped size, its attribution to crates or sections, and the bytes of the container image that carries it. It sits beside [timing.md](timing.md), [memory.md](memory.md) and [cpu.md](cpu.md) but is simpler than they are: a size is a property of an artifact, not of a run, so when the build is deterministic one build gives an exact count and the repetition, interleaving and confidence-interval rules of timing.md do not apply. What the standard adds is which size answers which question, which build inputs a size number has to state, when equal sizes prove nothing, and how far attribution tools can be trusted. Rules are numbered S1, S2, ...; each has a one-line reason and a citation. The evidence is the calibration in [binary-size-calibration](../binary-size-calibration/) (classes A-E on two static musl Rust web binaries, exact byte counts on one toolchain and host).

## Scope

The standard covers the size of a build artifact (file bytes, `PT_LOAD` segments, compressed bytes), the per-section and per-crate attribution of it, and the layer bytes of an image that holds it. It does not cover resident memory ([memory.md](memory.md)), start-up or run time ([timing.md](timing.md)) or CPU use ([cpu.md](cpu.md)). Every reported size states its rigor: **exact** when S3's conditions hold (identical inputs, one build, byte count), and otherwise the size is *not* a reproducible number and S3 sends it to timing.md's levels, where the sizes of several builds are treated as repeated measurements. A size reported from a calibration like the one cited here is exact for that toolchain image and host only; the calibration did not test other hosts or toolchain versions (S6).

## Rules

**S1. Name the question, then the size source.** Four questions are distinct. *Disk*: file bytes (`stat`). *Transfer*: the compressed bytes under the codec the file is served with (`gzip -9`, `zstd -19`), the codec and level stated. *Mapped memory*: the sum of the `PT_LOAD` `FileSiz` (bytes mapped from the file) or `MemSiz` (virtual size before any page is touched, an upper bound for resident memory and not a measure of it; resident memory is [memory.md](memory.md)). *Image*: layer bytes (S5). The `size -A` total answers none of them. Reason: in the calibration it counted `.bss` (21,792 B in the router, not in the file) and sections that are not loaded (`.comment`, `.dep-v0`), so it differed from the file by +14,670 B for one binary and -2,226 B for the other, while the `PT_LOAD` `FileSiz` sum was 99.84% of the file and the compressed forms were 33-44% of it. Citation: `binary-size-calibration/` class B table; `readelf(1)` and `size(1)` (GNU binutils); ELF specification, program headers (`p_filesz`, `p_memsz`).

**S2. State the build inputs with every number: toolchain image, target, `[profile.release]` settings, lockfile and build id.** Give the compiler and base image with versions, the target triple and linkage (static musl against dynamic glibc), every `[profile.release]` setting that applies (`opt-level`, `lto`, `codegen-units`, `panic`, `strip`, `debug`), whether the build was `--locked` and used the committed lockfile, the tool that built it (a plain build or `cargo auditable build`), and the build id (`GIT_SHA` or equivalent) with the source commit. A size contrast changes one setting and says so; a row that changes two (the `debug` row also needs `strip=false`) says that too. Reason: in the calibration the profile moved the file from -39.7% (`opt-level=z`) to +53.7% (`strip=false`) and +778.5% to +840.6% with `debug=true`, a setting's percent differed between crates (`opt-level=s` -37.5% against -24.5%), and `.text` and the file did not always move together (`lto=off`: tracker `.text` -2.49% while its file +0.62%), so a claim that omits a setting or names only the file or only `.text` can be wrong about the other. The glibc target was 2.3-2.4% smaller but changes the C library, allocator and linkage, so it is a target contrast, not a profile one, and ignores the libc an image must then carry. Citation: `binary-size-calibration/` class C table and its E1 paragraph; Cargo Book "Profiles" (`opt-level`, `lto`, `codegen-units`, `panic`, `strip`, `debug`).

**S3. Exactness: identical inputs give an exact size from one build; any changed input makes equal size no evidence of an equal artifact.** With the same sources, lockfile, toolchain image, settings and build id, a clean rebuild is byte-identical; report the byte count from one build and do not repeat it. When any input differs, compare artifacts by their hash (SHA-256), never by size alone, because size can match while content differs. If a size turns out non-deterministic (two identical-input builds differ), the exactness claim fails for that toolchain and the size is treated as a repeated measurement under [timing.md](timing.md): several builds, a spread, and its levels. Reason: three clean `--no-cache` builds of each of two binaries gave the same SHA-256 and 0 differing bytes (router 5,618,832 B; tracker 7,281,208 B), unaffected by host load, while changing only the build id changed 118,101 (router) and 660,661 (tracker) bytes and changing only the package version changed 2,262,964 and 2,648,156 bytes, with the file size and the `.text` size identical in every variant (the `size -A` sum even moved by +3 and +2 from alignment). Citation: `binary-size-calibration/` class A tables (the evidence is the calibration only; no external reference is claimed for determinism in general).

**S4. Attribution is a share of a stated denominator with its unattributed residue; each tool is reported against its own build.** Say what the percentages are of (`.text`, the file, the loaded VM size), name the tool and version, and report the unattributed part alongside (`[Unknown]` for `cargo-bloat`; `[Unmapped]` and non-DWARF buckets for `bloaty`). Attribution needs an unstripped build, and `cargo-bloat` rebuilds with plain `cargo build`, so its totals refer to that build and not to the shipped stripped artifact. Per-compile-unit data needs a debug-enabled companion build (`debug=true`, `strip=false`) and is not comparable with the stripped artifact; on a non-debug build the compile-unit table is misleading, and on the stripped binary `bloaty -d compileunits` fails. Reason: `cargo-bloat` attributed 93.7-99.0% of `.text` to crates but with `[Unknown]` at 14.2-37.9% of `.text` (mostly C code and symbols it cannot place), its file total differed from the driver build by -2,168 B, -1,440 B and +7,568 B, and `bloaty` summed to its own file total by construction (it adds buckets to account for every byte) with its VM total equal to the `PT_LOAD` `MemSiz` sum; with the `nostrip` build bloaty found 233 and 293 compile units with 5.66% and 50.11% of the file in non-DWARF buckets, against 486 and 357 units with 4.94% and 3.25% in the `debug` companion. Citation: `binary-size-calibration/` class D table and notes; bloaty and cargo-bloat documentation (References).

**S5. Report image bytes separately from binary bytes, and say unpacked or compressed.** An image number names its layers, whether it is the unpacked layer bytes (`docker history --human=false`) or the compressed layer blobs (`docker save` or a pull), and the image store. The store's reported `.Size` is neither, and the binary's share of the image is stated as a share of a named total. Reason: the same binary was 96.53% of a `scratch` image's unpacked layer bytes and 18.97% of an `alpine` image's (base, `apk` packages and assets are the rest), the binary layer was larger than the file by tar overhead (5,623,808 against 5,618,832 B), and the containerd `.Size` (8,399,821 and 56,057,160 B) equalled the unpacked layer bytes plus the compressed blobs, so it is neither a disk nor a download number. Citation: `binary-size-calibration/` class E table; Docker documentation for `docker history` and `docker save` (References).

**S6. State the scope limits.** Exactness (S3) was shown on one toolchain image (Rust 1.99.1, Alpine 3.24), one Docker and BuildKit, one host, and two crates built from one profile. Cross-host determinism (CPU count, Docker version, base-image rebuilds with newer packages such as `musl-dev`) and other toolchain versions were not tested, and a later point release of the C library can change bytes. A claim on another toolchain or host re-runs the three-build identity check (S3) before relying on one build per number. Settings' percentages are per-crate properties, not constants; the calibration's variants ran with a warm cache, and only the determinism builds were `--no-cache`. Reason: those are exactly the conditions the calibration varied or held fixed, and nothing outside them was measured. Citation: `binary-size-calibration/` Limits section.

## Reporting checklist (in addition to timing.md's where S3 falls back to it)

A size claim in an investigation README states:

- The question and the size source (S1), and for compressed sizes the codec and level.
- Toolchain image, target and linkage, builder, every `[profile.release]` setting, lockfile and build id with the source commit (S2).
- Whether the number is exact (identical inputs, one build) and the hash that identifies the artifact; for a comparison between builds, which input changed (S3).
- For attribution: tool and version, the build it ran against, the denominator, the unattributed residue, and for compile units the debug companion build (S4).
- For an image: unpacked or compressed, per layer, the store, and the share's denominator (S5).
- The scope limits that apply, in particular any toolchain or host not covered by an identity check (S6).
- Deviations from S1-S6 and why.
