# Memory measurement standard

This is the method every memory claim in this repository follows: peak memory, settled (steady-state) memory and growth across repeated cycles of a process or container. It extends [timing.md](timing.md), whose rules R1-R11 (repetition, interleaving, padding, bootstrap CIs, A/A floor, claim rule, fixed sample size, environment record) apply to memory metrics unchanged, and [live-host.md](live-host.md) when the host is a live workstation. What it adds is which memory source answers which question, what each source counts beyond the workload, and the Docker and allocator effects that move a memory number without the workload changing. Rules are numbered M1, M2, ...; each has a one-line reason and a citation. The evidence is the calibration in [memory-measurement-calibration](../memory-measurement-calibration/) (classes a-d, standard rigor with one stated R5 exception: one build per variant, so layout variation is limited to environment padding) and the daemon memory class of [live-host-measurement-confounds](../live-host-measurement-confounds/).

## Scope: rigor follows use

The two levels of [timing.md](timing.md) (Scope) apply as written. **Indicative** memory numbers (sizing, a spike, a sanity check) are a few runs reported with the label *indicative*, the source and the command; they never carry a precise ratio or a "uses N% less" claim. **Standard** is this document's rules M1-M9 on top of timing.md's R1-R11 and both reporting checklists, run through `scripts/measure.mjs` with `scripts/memprobe.sh`; it is required whenever memory cost is the product of the research or the claimed separation is small against the run-to-run spread or against the offsets of M2. Every reported memory number states its rigor level and its source.

## Rules

**M1. Name the question, then the source.** Three questions are distinct and each has its own source. *Peak*: the highest memory the workload reached; per process, `VmHWM` (`vmhwm_mib`); per container, `memory.peak` (`cgroup_peak_mib`) or the sampled `anon` high-water (`cgroup_anon_hwm_mib`). *Settled*: the steady state after the workload signals it is complete, read at a stated window after that boundary (M5); per process `RssAnon` (`rssanon_settled_<S>s_mib`), per container cgroup `anon` (`anon_settled_<S>s_mib`). *Growth*: the change of a settled value across repeated cycles of the same workload inside one process, reported as a slope over cycle count, never as one before/after pair. Reason: in the calibration the sources answer different questions and differ by fixed offsets of 0.1-9.5 MiB at the same allocation (class a table), so a number without its source and question cannot be compared. Citation: calibration class a; `proc(5)` (`VmHWM`, `RssAnon`); kernel `Documentation/admin-guide/cgroup-v2.rst` (`memory.peak`, `memory.stat`).

**M2. Report differences against a zero-allocation control, or slopes, not raw absolutes.** Every source carries a constant offset beyond the workload: `memory.peak` includes the container's start-up charge (about 9.5 MiB, present for the 0 MiB program and not sampleable by the probe) and the probe itself (about 1.4 MiB, class d); cgroup `anon` includes container start-up anon (5.91 MiB for the empty workload); `VmHWM` includes the process's resident file pages (about 1.4 MiB of binary and libc) and covers one process only; process `RssAnon` carries 0.11-0.12 MiB. Run a variant of the same program that allocates nothing and subtract it, or fit a slope across known sizes, whenever an absolute size matters. Reason: with offsets removed, process `RssAnon` minus the 0 MiB variant recovered 16/64/256 MiB within 0.02 MiB and the cgroup anon high-water recovered the 240 MiB difference between a256 and a16 exactly, while no raw median contained the known size. Citation: calibration class a (`cgroup_peak_mib` +9.3/+9.4/+9.7, `vmhwm_mib` +1.4, `anon_settled_0s_mib` +0.30) and class d (`self_cgroup_peak_mib` probe/bare 1.019 [1.016, 1.024]).

**M3. `memory.peak` is not a process-memory number when the workload touches files.** `memory.peak` and the cgroup `file` counter include page cache charged to the cgroup, including files the workload writes. When the workload does file I/O, report cgroup `anon` separately from `file` (`cgroup_file_hwm_mib`), or use a process source (`VmHWM`, `RssAnon`), and state which. Reason: a buffered 256 MiB write raised `cgroup_peak_mib` by 257.7 / 258.0 MiB over the same allocation without the write and `cgroup_file_hwm_mib` by exactly 256 MiB, while anon and `VmHWM` moved only by the writer's own 1.0-1.3 MiB buffer and stack. Citation: calibration class b; kernel cgroup-v2 docs (`memory.stat` `file`).

**M4. Measure the container from inside, one fresh container per invocation.** In a container the cgroup filesystem is read-only, so `memory.peak` cannot be reset between workloads, and the container's cgroup scope is removed when it exits, so any host-side reader must sample before removal. Run the probe inside the container around the measured command (`memprobe.sh -- cmd`), one throwaway `docker run --rm` per invocation, so each invocation's `memory.peak` covers exactly one workload. Reason: a peak that cannot be reset accumulates every earlier workload in that container, and a scope read after exit does not exist. Citation: calibration Method and "What each source counts"; kernel cgroup-v2 docs (`memory.peak`).

**M5. Settled values only after a workload-complete boundary, at stated windows.** The workload signals completion (a line on stdout or a marker file) while it is still alive; settled values are read at stated offsets S after that boundary (`--settle S[,S...]`), several windows in the same block, and only while the process stays alive through each window. Without a boundary, or for a window the process does not survive, the settled metric is unsupported and not reported; a time series from launch or after exit is never a settled value. Each settled number states its window, and the window is justified for the workload: a window that is too short measures memory not yet released. Reason: on the real daemon of the live-host investigation, settled anon kept falling between 30 s and 120 s idle, so the bad-mode rate read 0.70-0.90 at 30 s against 0.35-0.75 at 120 s; the calibration's synthetic churn did not settle at all between 0 and 120 s (windows agree within 0.9 MiB), so it shows the boundary mechanism works but gives no evidence for any particular window length. Citation: live-host-measurement-confounds K3 (`badmode.tsv`); calibration class c; `memprobe.sh --help`.

**M6. State the allocator, its tunables and the cpuset with every settled or peak number.** glibc creates malloc arenas per thread up to a limit that scales with the CPU count, and retained memory depends on the arena count and the trim threshold (`MALLOC_ARENA_MAX`, `M_TRIM_THRESHOLD`). Report the allocator and version, every tunable set (environment or `mallopt`), the thread count and the cpuset; compare variants only under the same settings unless the setting is the variable. Reason: in the calibration capping arenas at 2 (2 arenas instead of 13) cut retained anon by 6.7% (ratio 0.9327 [0.9288, 0.9359], about 28 MiB) after the same churn, while moving the cpuset between 2, 6 and 12 CPUs moved it by 0.2% or less with 13 arenas everywhere (12 worker threads), a small but resolved effect. Citation: calibration class c; glibc manual "Memory Allocation Tunables".

**M7. Multimodal metrics are reported as a rate, per LH6.** When a settled value is bimodal (an allocator that sometimes keeps memory), do not report its median; define the bad mode by a threshold fixed before the claim-producing run (from a pilot, excluded from inference), emit it per invocation as a 0/1 metric, and report it with the driver's `rate` kind: k/n with a Clopper–Pearson interval, comparisons as a difference in proportions with a Newcombe interval, and the A/A pair's difference half-width as the floor ([timing.md](timing.md) R6-R8 rate carve-out; the block count and window rules are [live-host.md](live-host.md) LH6). Twenty blocks per condition resolve only large rate differences. Reason: the daemon's median contrasts were unresolved everywhere (A/A floors of 13-26%) while its rates were measurable; in the calibration 0/20 gives a Clopper–Pearson upper bound of 0.168 and an A/A Newcombe half-width of 0.161, which is the resolution of 20 blocks, not a measured bad-mode rate (that churn was unimodal). Citation: live-host-measurement-confounds K3; calibration class c; timing.md R6-R8.

**M8. Every memory metric has a driver `metrics` entry.** In the `measure.mjs` config, each memory metric gets `{ "kind": "level", "better": "lower" }` (or `"rate"` for a 0/1 bad-mode metric), and metric names are the ones `memprobe.sh --help` prints (`cgroup_peak_mib`, `cgroup_anon_hwm_mib`, `cgroup_file_hwm_mib`, `vmhwm_mib`, `anon_settled_<S>s_mib`, `rssanon_settled_<S>s_mib`). Reason: a metric without an entry is treated as a time and its verdicts read "faster"/"slower"; fixed names keep reports comparable across investigations. Citation: timing.md "Using the driver"; calibration configs (every metric has an entry).

**M9. Heap profilers attribute, they do not measure.** Tools such as heaptrack or valgrind massif answer *which allocation site* holds memory; the reported size always comes from the sources of M1 in an unprofiled run. Reason: a profiler interposes on or replaces the allocator and slows the program, so it changes both the memory it reports and the timing that drives allocator retention (M5, M6). Citation: calibration Limitations (heap profilers were not used, so no calibrated profiler number exists); glibc manual "Memory Allocation Tunables" (allocator behaviour depends on its configuration).

## Reporting checklist (in addition to timing.md's)

An investigation README with a memory claim states:

- Rigor level (Scope) and, per metric, its source (`memory.peak`, cgroup `anon`/`file`, `VmHWM`, `RssAnon`) and the question it answers (peak, settled, growth) (M1).
- The zero-allocation control or the slope used to remove offsets, or why absolute values are acceptable (M2).
- Page-cache handling: whether the workload does file I/O and how `file` was separated from `anon` (M3).
- Container setup: probe inside, one fresh container per invocation, sampling interval (M4).
- The boundary signal and every settle window with its justification (M5).
- Allocator and version, tunables, thread count and cpuset (M6).
- For multimodal metrics: the threshold and its pilot, and the rate report per timing.md's rate rows and LH6 (M7).
- The driver `metrics` map (M8).
- Deviations from M1-M9 and why.
